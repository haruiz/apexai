Implementation timeline

ApexAI evolved from a telemetry replay prototype into a field-tested, offline edge coaching system. This timeline highlights how each implementation changed from the first deliverable through the Sonoma Raceway field test and final project wrap-up.

  1. Project start

    Telemetry replay foundation

    Built the first FastAPI telemetry server around Racelogic VBOX replay so recorded laps could be streamed like live car data, matching the simulator foundation described in the root README.

    • Parsed `.vbo` sessions into normalized telemetry packets.
    • Added throttled or timestamp-based replay for repeatable simulation.
    • Established the FastAPI telemetry contract later used by SSE and WebSocket clients.
  2. April 29

    Architecture/code review & travel approval

    Presented the first deliverable for architecture and code review, then secured approval to take the system into the Sonoma Raceway field-test phase.

    • Reviewed the `src/apexai/server/` telemetry server and replay pipeline.
    • Validated the `ui/` dashboard as the simulator and visualization harness.
    • Confirmed the Android app path for memory-driven, in-car edge coaching.
  3. Pre-field-test integration

    Memory bank and edge coach split

    Split heavy analysis from in-car execution by moving coaching reasoning into exportable memory banks and keeping the Android app focused on low-latency local decisions.

    • Implemented React/Vite + Express dashboard flows for ideal-line and rule generation.
    • Used the Rust `dashboard/data-engine/` parser and WASM rule evaluator for sector-aware analysis.
    • Exported `latest.json` memory banks with deterministic and Gemini-assisted recommendations.
  4. May 23

    Field test at Sonoma Raceway

    Validated the full workflow at Sonoma Raceway using real driving telemetry, trackside analysis, and the in-car coaching loop as the main driver-facing runtime. The app was successfully tested and the coaching flow worked in practice.

    • Collected real telemetry for replay, debugging, and memory-rule refinement.
    • Validated the mobile ingestion path from simulator telemetry and CANable/CAN data.
    • Observed GPS-dependent sector lookup as the main field reliability challenge.
    • Compared two same-day driving sections: cloudy sky produced weak GPS, while sunny open-sky conditions produced accurate sector matching.
  5. May 30

    Project concludes

    Closed the project with the post-Sonoma implementation updates folded into the final documentation and architecture narrative.

    • Documented `VBOTelemetrySource`, `CanRawChunkTelemetrySource`, and `CanDecodedTelemetrySource` support.
    • Captured mobile dual-coach behavior: `HeuristicBaseAICoach` and `GemmaCoach` over the same memory bank.
    • Identified GPS resilience as the key future improvement for memory-note activation on track.
    • Grounded the final architecture in the dashboard, root, and mobile README component contracts.
  6. Future improvement

    GPS resilience for memory-note activation

    Improve sector-level memory activation when GPS signal quality drops, so the coach can stay reliable in cloudy or obstructed track conditions.

    • Add fallback sector estimation using telemetry continuity and lap progress.
    • Blend GPS with speed, heading, distance integration, and CAN-derived signals.
    • Use confidence scoring before activating sector-level memory notes.
